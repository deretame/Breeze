# Breeze 插件评论系统设计草案

状态：讨论稿，尚未实施。

日期：2026-09-03。

本文记录不同图源评论模式的统一设计思路，作为后续讨论、协议细化和实现的依据。下文的新字段和接口参数仅用于说明语义，不代表已经发布的插件协议；最终命名、版本协商和迁移细节仍需在实现前确定。

## 1. 背景与目标

Breeze 通过插件聚合不同图源，各图源的评论模式并不一致：

- 只有普通评论，不能回复。
- 主评论下可以回复，但不能继续回复楼内评论。
- 可以回复任意一条评论，包括回复的回复。
- 回复与普通评论一起出现在主列表，通过引用原文说明回复对象。
- 主列表与楼内列表并存，同一条回复可能出现在多个入口。

如果平台只保留所有图源的共同功能，多级回复、引用和点赞等能力就会丢失。如果每个图源都单独实现页面，界面与维护成本又会持续增加。

建议统一评论的表达方式和操作语义，通过可选能力保留图源差异，由平台组合通用界面。目标是保留图源能够明确提供的功能和关系，不要求完全复刻原网站的页面。

第一阶段聚焦评论阅读与发送，包括普通评论、回复、引用上下文和分页。点赞、编辑、图片等作为后续扩展；不在本阶段引入任意插件 UI、通用动作脚本或跨图源评论合并。

## 2. 当前实现

以下结论来自当前工作区的源码阅读，未进行图源接口或实际运行验证。

| 位置 | 当前职责与行为 |
| --- | --- |
| `lib/page/comments/model/comment_item.dart` | `CommentItem` 包含作者、正文、时间、`replyCount`、递归 `replies` 和 `extern`；没有直接回复对象、讨论串归属或引用摘要字段。 |
| `lib/page/comments/cubit/comments_cubit.dart` | 调用 `getCommentFeed`、`loadCommentReplies`、`postComment` 和 `postCommentReply`；管理主列表、置顶列表与各评论的回复分页。 |
| `lib/page/comments/view/plugin_comments_scaffold.dart` | 展示主评论与一层回复；通过 `!isReply` 限制楼内评论继续展开或被回复。 |

当前已有以下基础：

- `canComment.comic` 和 `canComment.reply` 控制评论与回复入口。
- `replyMode` 区分 `embedded` 与按需加载；当前 `embedded` 分支把随评论返回的回复视为完整列表。
- 主列表与回复列表分别维护页码和 `hasReachedMax`。
- 回复操作把所选评论的 `id` 与 `extern` 交给插件。
- 发送结果可通过 `created` 和 `insertHint` 更新列表，也可以要求重新获取数据。

后续设计可以沿用这些入口逐步演进。主要需要补齐的是关系语义、列表范围、预览完整性和每条评论的操作状态，而不是仅放开界面中的 `!isReply` 限制。

## 3. 分开表达关系、列表组织与操作能力

一条评论需要分别回答三个问题：

1. 它回复了谁，属于哪段讨论，引用了什么内容？
2. 它出现在什么列表，这个列表如何继续加载？
3. 当前用户可以对它执行什么操作？

这三个维度可以组合，不使用单一的“普通 / 二级 / 多级评论”模式枚举承担所有语义。

| 图源模式 | 关系表达 | 列表组织 | 交互方式 |
| --- | --- | --- | --- |
| 普通评论 | 无回复关系 | 主列表 | 按能力提供发表评论入口 |
| 主评论加一层回复 | 回复指向主评论 | 主列表与独立回复列表 | 展开回复，仅允许回复适用对象 |
| 多级回复 | 直接回复对象与讨论串归属分别提供 | 整段讨论平铺，或逐条加载直接回复 | 可以回复楼内评论，按需查看上下文 |
| 回复混在主列表 | 保留回复关系和引用摘要 | 保持主列表顺序 | 卡片展示“回复某人”和原文引用 |
| 主列表与楼内列表并存 | 同一评论使用一致标识 | 每个列表独立维护成员和分页 | 同一评论的内容及状态保持一致 |

`embedded` 和按需加载只描述数据获取方式，不应同时决定回复层级、主列表是否包含回复或用户能否回复。

## 4. 评论数据与关系

### 4.1 基础评论与标识

统一评论对象保留现有作者、正文和时间等基础字段。第一阶段正文继续以文本为主，后续有实际需求时再定义图片、表情等内容块。

评论标识由插件提供，平台按图源和评论区上下文限定作用域。不同图源、不同漫画中相同的 `id` 不能直接视为同一条评论。插件应在其声明的作用域内提供稳定、唯一的标识；平台不根据正文或列表下标猜测身份。

平台可以分别维护评论内容和各列表中的评论标识顺序。同一条回复同时出现在主列表与讨论详情时，允许出现在两个列表中；去重应在各自列表内进行，不能因为别处已经显示就把它隐藏。

### 4.2 直接回复对象与讨论串归属

建议明确区分以下概念，字段名暂定：

| 字段 | 含义 | 缺失时的含义 |
| --- | --- | --- |
| `replyTo` | 直接回复对象的引用，可包含标识和作者摘要 | 没有提供可用的直接回复信息；不能据此断定是主评论 |
| `threadRootId` | 所属讨论串的起始评论标识 | 图源未提供或插件无法确认，不由平台自动推断 |
| `quotes` | 被引用内容的摘要或快照 | 没有提供结构化引用内容 |

例如：

```text
A：这章结尾是什么意思？
B 回复 A：可能是在暗示下一章。
C 回复 B：但上一章不是已经解释了吗？
```

C 的直接回复对象是 B，讨论串起点是 A：

```json
{
  "id": "C",
  "content": "但上一章不是已经解释了吗？",
  "replyTo": {
    "id": "B",
    "authorName": "读者乙"
  },
  "threadRootId": "A"
}
```

主评论本身若已确认是讨论串起点，可让 `threadRootId` 等于自身标识。图源只提供“回复某用户”时，可以保留作者摘要而不提供评论标识；界面展示已知信息，不生成虚假的原文跳转入口。

不让一个 `parentId` 同时表示直接回复对象、讨论串起点和发送后应插入的列表。这三个值在多级回复场景中可能完全不同。

### 4.3 引用与回复不能互相推断

引用内容可以包含原作者、正文摘要、可选的原评论标识，以及图源明确提供的原文状态。

- 有引用文本，不一定意味着图源建立了正式回复关系。
- 有回复关系，也不一定能取得原文内容。
- 引用快照不一定等于原评论的最新内容，不直接覆盖原评论实体。
- 只有摘要而没有定位能力时，引用块仅展示摘要。
- 图源明确返回已删除或不可见时，展示对应占位状态；普通请求失败显示加载失败。

正文中的 `@某人` 或“回复某人”文本不能作为平台推断父子关系的依据。图源特有格式由插件在有明确依据时转换。

### 4.4 回复数量与预览

回复列表的范围应明确为“这条评论的直接回复”或“整段讨论中的所有回复”。数量必须与对应范围一致，不能把两者混用。

需要区分：

- 已知为零条回复。
- 数量未知，但图源提供了可加载的回复入口。
- 已返回部分预览，还有后续内容。
- 已返回全部回复。
- 尚未加载或加载失败。

未知数量不强制转成 `0`，是否显示“查看回复”也不只取决于 `replyCount > 0`。内嵌回复只是数据已随本次响应返回，不天然表示完整；应同时说明列表范围、完整性及下一页信息。

## 5. 图源能力与当前操作状态

能力需要分成两层：图源是否支持，以及当前上下文是否允许。

| 层次 | 示例 | 用途 |
| --- | --- | --- |
| 图源能力 | 发表评论、回复、读取回复列表、读取单条原文、点赞 | 表达插件能提供哪些操作 |
| 当前操作状态 | 可用、需要登录、评论已锁定、当前用户无权操作 | 决定当前页面或评论上的入口状态 |

发表评论的操作状态属于评论区；回复、删除等状态属于具体评论。某个源支持回复，并不代表它支持回复所有楼内评论。是否显示回复入口应看目标评论的状态，不由界面嵌套层级决定。

交互建议：

- 不支持的功能不显示入口。
- 需要登录的功能可以保留入口，并在触发时引导登录。
- 被锁定或无权限时显示明确原因，避免用户反复提交。
- 服务端在提交时仍可能拒绝请求，界面中的操作状态不是成功保证。

后续可按相同规则增加点赞、编辑、删除、图片发送等能力。第一版只定义实际接入的操作，不预先设计可以执行任意行为的动作系统。

## 6. 列表加载与分页

### 6.1 每次加载对应一个明确范围

主评论流、讨论串列表和某条评论的直接回复列表可能是不同的数据集合。插件需明确每个入口的范围，平台不能默认 `loadCommentReplies` 一定返回所有后代或只返回直接子评论。

现有语义入口可继续作为演进基础：

| 入口 | 建议职责 |
| --- | --- |
| `getCommentFeed` | 读取当前评论区主列表，说明包含主评论还是混合评论流，保留置顶区域语义 |
| `loadCommentReplies` | 按明确的回复范围读取列表，并返回独立分页信息 |
| 可选的原文读取入口 | 按引用定位单条评论或上下文；具体名称待协议细化 |

读取列表、读取原文与发送回复是独立能力。能回复某条评论，不代表图源一定提供按该评论查询所有回复的接口。

### 6.2 分页凭据由插件解释

建议逐步允许插件返回不透明的下一页凭据，以适配页码、游标和其他分页方式。平台负责保存和原样传回，插件负责转换为图源请求。

列表响应至少应表达本页条目与是否存在下一页；新协议应约定清楚：首次请求不传续页凭据，后续凭据只用于当前列表，终止状态不依赖“这一页条目少于预期”的猜测。

分页状态按图源、评论区、列表范围、排序条件和必要的登录上下文隔离。切换排序或账号后重新加载，不能沿用此前的续页凭据。

主列表和各回复列表分别维护加载中、已加载、加载失败、已到末页等状态。某个回复列表失败不清空主列表，重试也不把失败解释成零条回复。

### 6.3 保留图源返回的列表成员与顺序

平台不依据回复关系把主列表中的回复自动搬到其他评论下面，也不跨页重新构建完整评论树。

例如，第一页出现 C，但它回复的 B 在第十页：C 仍应正常展示，已有摘要直接用于引用块；支持原文读取时再按用户操作查询 B。

图源只提供逐条查询直接回复时，平台可以逐步展开或进入下一层详情，但不能为了得到“整段讨论”自动递归抓取所有评论。图源直接提供完整讨论流时，平台可以平铺展示。

置顶列表与普通列表发生重复时，需要明确展示规则，例如保留置顶位置并隐藏普通区域的重复项。该展示去重不改变服务端分页凭据，也不影响同一条评论出现在独立的讨论详情中。

## 7. 发表评论与回复

用户点击哪条评论的回复按钮，平台就把哪条评论作为直接目标交给插件，同时携带已知的讨论串归属和该目标的插件上下文。

对于“C 回复 B，属于 A 的讨论串”，输入框应提示正在回复 B。插件根据图源要求转换为直接父评论标识，或主评论标识加被回复用户标识等参数；平台不把目标静默替换成 A。

可继续利用现有 `extern` 传递图源所需的额外信息，但明确边界：

- 通用展示和关系使用正式字段表达。
- 图源请求所需的专有标识由插件解释，平台原样传递。
- 平台不按图源名称分支，也不解析 `extern` 来决定引用关系或按钮行为。

发送结果应明确区分成功、待审核和失败，不能把请求受理一律显示为已公开发布。网络超时导致结果不确定时，不自动重复发送。

发送后的列表更新沿用现有 `created` / `insertHint` 思路，但需要指明受影响的列表范围：

- 确定新评论属于哪个列表及其位置时，更新对应列表，并按标识去重。
- 直接回复对象与插入目标列表分别表达。例如回复 B，但插入 A 的讨论流。
- 无法确定排序位置时重新获取受影响列表，避免默认插入主列表顶部。
- 发送成功后刷新失败，分别反馈这两个结果，不提示用户再次发送。
- 待审核的内容明确标记状态，不假装已经出现在公开列表。

## 8. 平台界面组合

平台提供统一的评论卡片、引用块、输入框和回复列表，由数据与能力决定组合方式。

| 场景 | 建议展示 |
| --- | --- |
| 普通评论 | 基础评论卡片，按能力展示操作 |
| 主列表中的回复 | 卡片显示“回复某人”，有摘要时附带引用块 |
| 主评论附带回复 | 展示少量回复预览，并提供继续查看入口 |
| 多级回复 | 讨论详情中展示回复对象，按需查看原文或进入下一级列表 |
| 原文只有快照 | 展示引用摘要，不提供无法完成的跳转 |
| 原文不可见 | 展示图源确认的不可见状态，当前回复仍保留 |

数据可以有多层关系，手机界面不必无限向右缩进。优先控制可视缩进，通过“回复某人”和上下文详情保留交流关系。

平铺整段讨论的前提是已取得对应范围的数据；界面不能因为选择了平铺样式，就假定逐条回复接口已经返回全部后代。

输入框应保留明确的回复对象提示。发送失败保留用户输入，查看原文或收起回复列表不应意外丢失草稿。

## 9. 兼容与实施范围

本草案建议逐步演进当前评论协议，不直接把新语义套在旧字段上。

| 现有字段或行为 | 演进方向 |
| --- | --- |
| `canComment.comic / reply` | 保留兼容读取，新增图源能力与当前操作状态；旧插件不能据此被推断为支持回复楼内评论 |
| `replyMode` | 保留旧版内嵌与按需加载解释；新版另外说明列表范围、预览完整性和布局信息 |
| `replies` | 在新版中明确是哪个列表的预览或完整数据，不仅依靠递归结构推断关系 |
| `replyCount` | 新版允许未知，并明确统计范围；旧版默认值不应被宣传为准确统计 |
| `page / hasReachedMax` | 旧插件维持页码协议，新协议按版本或能力协商支持续页凭据 |
| `parentId / insertHint` | 拆清直接目标、讨论串归属和待更新列表，保留明确的旧版适配规则 |
| `extern` | 继续承载插件专有请求上下文，通用语义逐步进入正式字段 |

第一阶段建议完成：

1. 明确普通评论、直接回复对象、讨论串归属和引用摘要。
2. 明确主列表、直接回复列表和讨论流的范围及独立分页。
3. 支持完整内嵌列表与部分预览，区分未知数量和零条回复。
4. 按目标评论的实际状态提供回复入口，保留准确发送目标。
5. 实现普通、楼内、多级和混合流的通用展示组合。
6. 为旧插件提供兼容路径，再选择实际图源逐个验证。

后续根据实际需求增加点赞、编辑、删除、图片或其他内容能力。即使图源功能更丰富，也可以暂时只声明平台已经支持的部分；新的通用能力经定义后再扩展。

## 10. 实现前待确认的问题与验证场景

实现前需要进一步确认：

- 协议版本如何协商，旧插件的默认行为如何保持。
- 实际图源分别提供直接回复列表、整段讨论流还是混合主列表。
- 回复数量、内嵌列表完整性、置顶重复项的真实接口语义。
- 直接目标、讨论串和引用字段的最终形状，以及原文定位方式。
- 首版讨论详情使用新页面还是弹层，如何保持列表位置和草稿。

后续实现至少验证以下场景；这是验证计划，不代表已经执行：

| 场景 | 预期结果 |
| --- | --- |
| 图源只有普通评论 | 正常阅读，回复入口不出现 |
| 图源只允许回复主评论 | 主评论可回复，楼内评论不出现错误入口 |
| C 回复 B，B 属于 A | 提交目标为 B，讨论归属为 A，插入位置按返回结果确定 |
| 回复出现在主列表 | 保持位置和排序，准确展示引用，不自动移入其他列表 |
| 原评论不在已加载页 | 当前回复正常显示；只有受支持的定位操作才发起查询 |
| 内嵌数据仅为预览 | 可以继续加载，不把预览当成全部回复 |
| 回复数量未知但存在读取入口 | 可以查看回复，不显示伪造的零条计数 |
| 主列表和不同回复列表同时分页 | 状态互不覆盖，失败可单独重试 |
| 同一回复出现在多个列表 | 各列表正常展示，单列表内不重复，实体更新保持一致 |
| 原文已删除或权限受限 | 保留当前回复，按已知事实展示引用占位 |
| 发送成功但刷新失败 | 明确提示已发送与刷新失败，不诱导重复提交 |
| 发送超时或进入审核 | 不自动重发，不把未知结果或待审核状态当成已公开 |
